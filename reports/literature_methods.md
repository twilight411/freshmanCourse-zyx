# Primary-source synthesis: five Text-to-SQL papers

**Status:** literature review only; no experiment has been run for this report. **Access date:** 2026-11-04.

I read the arXiv HTML full texts of the five papers below, with the PDFs retained for table checks. Claims are cited to the paper URL and the relevant section/table. I did not use secondary summaries or leaderboard commentary.

| ID | Paper (arXiv URL) | Version read |
|---|---|---|

| P2 | [SQL-Trail: Multi-Turn Reinforcement Learning with Interleaved Feedback for Text-to-SQL](https://arxiv.org/abs/2601.17699) | v1, 25 Jan 2026 |

## 1. Bottom line

- **Among these five, only one paper is conversational multi-turn:** P3 evaluates CoSQL and SParC, where each user turn is conditioned on dialogue history and prior SQL [P3 §3.1, §4.1]. P2 uses the phrase “multi-turn” for repeated agent–database interactions on independent, single-turn BIRD/Spider questions [P2 §3.1, §4.3]; that is not conversational Text-to-SQL. P1, P4, and P5 have single-turn task settings.
- **“Execution feedback” means different things:** P1 uses execution only to label training pairs and does not execute at test time [P1 §3.3]. P4 and P2 execute during decoding/inference [P4 §3.2; P2 §3.1]. P5 executes for checking and repair at inference [P5 §3.5]. P3 executes against both a database and a dialogue-memory tool [P3 §3.1, §3.3.2].
- **The published scores are not a leaderboard.** They differ in base model, training data, number of test-time candidates, execution access, and benchmark split. None of the five evaluates BIRD Mini-Dev 2026 or a DeepSeek API. The correct use of these numbers is within-paper, setting-specific evidence, not a cross-paper ranking.
- **Reproducibility is uneven:** P1 releases training code and model weights; P3 releases code and checkpoints; P2, P4, and P5 provide no code/model/data link in the versions read.

## 3. Keep the settings separate

**Task-setting definitions used here**

1. **Conversational multi-turn:** multiple user utterances; the system must resolve the current utterance against dialogue history and previous SQL. Only P3 is in this category [P3 §3.1].
2. **Single-turn with test-time interaction:** one user question, but the system may issue several SQL queries/repair calls before answering. P2, P4, and P5 belong here. Their “turns” are model/environment turns, not user turns [P2 §3.1; P4 §3.2; P5 §3.5].
3. **Single-turn one-pass:** one question, one generation, no test-time database access. P1’s inference is in this category, even though its training used execution labels [P1 §3.3].

**Non-transfer rules**

- **Never compare CoSQL/SParC EX or EM with BIRD/Spider EX.** P3’s 79.9 CoSQL EX is a conversational, multi-turn number; it says nothing about BIRD [P3 §4.2]. Conversely, P2’s BIRD 64.2 is single-turn-question/multi-agent-turn performance [P2 §5.1].
- **Never treat “BIRD dev” as BIRD Mini-Dev.** The papers evaluate the official BIRD dev/test splits [P1 §4.1; P2 §4.3; P4 §4.1; P5 §4.1]. Mini-Dev 2026 is a separate 500-question development set. A Mini-Dev score cannot be inserted into these tables.
- **Do not compare different decoding/test-time budgets.** P1’s 68.51 is a single model output [P1 Table 1]. P2’s 64.2 is majority@8 [P2 §4.3]. P4’s 64.9 is tree decoding with 16 candidates, while its greedy score is 63.4 [P4 Table 6]. P5’s 63.23 uses a multi-agent API pipeline with repair [P5 §4.1]. These are not the same inference budget.
- **Do not compare dev and test as if interchangeable.** P1 reports BIRD dev 68.51 and test 68.53, but they are different splits [P1 Table 1, Table 4]. P5 reports Spider dev 79.6 and test 82.8 [P5 Table 2]. Report the split explicitly.
- **Do not compare a cleaned/filtered subset with an official score.** P5’s 96.5/97.6 Spider numbers come after removing items judged to contain gold errors; its official Spider numbers are 79.6/82.8 [P5 §4.2, §4.3, Table 2]. The cleaned number is not a drop-in replacement for the official metric.
- **Do not compare different metrics as if they were EX.** P4’s BIRD VES 73.1 and Spider TS 83.7 are efficiency/test-suite metrics, not EX [P4 §4.1]. P3’s EM is exact string match, not execution match [P3 §3.3.2]. P1’s validity rate is not accuracy [P1 §4.1].
- **Do not rank rows by headline score.** Different base models (7B, 32B, 70B, API), training data (BIRD/Spider, Spider only, CoSQL/SParC), and test-time access make a single ranking meaningless. The table is a scoped description of five methods.

## 4. What each paper actually shows

**P1 ExCoT.** Execution accuracy can supervise preference learning without a reward model or human preference labels. GPT-4o generates diverse CoTs; only those whose final SQL matches the gold result are retained for SFT, and correct/incorrect solutions become DPO pairs; on-policy rounds regenerate from the evolving model [P1 §3.1–3.4]. The reported Llama-3.1-70B gain is 57.37→68.51 on BIRD dev and 78.81→86.59 on Spider test, with 68.53 on BIRD test [P1 §4.2, Table 1, Table 4]. The cost is substantial: 64 H100s, 448 GPU-h for SFT and 160 GPU-h for DPO, plus GPT-4o sampling [P1 §4.1]. A simple zero-shot CoT prompt did not help and in fact scored below the no-CoT base in Table 1 (57.37→52.61) [P1 §4.2, Table 1]. The method is single-turn and does not execute at inference [P1 §3.3].

**P2 SQL-Trail.** The paper’s contribution is an agentic, execution-interleaved RL loop for single-turn questions, not a conversational model. It distills 1,000 correct multi-turn trajectories from Claude-3.7 on Spider, then runs GRPO on 1,027 selected questions with a six-term reward [P2 §3.2–3.3, §4.2, App. A.6]. Its strongest evidence is data efficiency and cross-domain transfer: 7B BIRD dev 60.1 greedy/64.2 majority with 1,873 training examples, and a controlled single-pass vs multi-turn comparison of 56.3 vs 59.3 majority EX on BIRD dev [P2 §5.1, Table 2]. The paper explicitly notes that multi-turn interaction increases inference cost and requires database access [P2 §7]. No code, weights, or data link appears in v1.

**P3 MTSQL-R1.** This is the only true conversational multi-turn paper in the set. It formulates each user turn as an MDP with two environments: the database for execution and a persistent dialogue memory for coherence checking [P3 §3.1]. It combines self-taught SFT with GRPO and process rewards for SQL clauses and verification actions [P3 §3.2–3.3]. With Qwen3-4B it reports CoSQL 79.9 EX/65.2 EM and SParC 79.0 EX/68.7 EM [P3 §4.2, Table 2]. Important caveat: the standard multi-turn evaluation feeds ground-truth prior SQL into the history; when prior SQL is model-generated, CoSQL EX falls to 76.5, still above the 71.2 baseline [P3 §4.2, Table 6]. The paper trains on a single 8×A100 node and releases code plus checkpoints [P3 App. C, abstract, title note 1].

**P4 ReEx-SQL.** This paper makes execution feedback part of decoding, not a post-hoc correction stage. The model emits `<intermediate_sql>`, receives results/errors, and continues until `<final_sql>`; GRPO uses format, exact-match, execution, entity-match, and exploration rewards [P4 §3.2–3.3]. The clean comparison is against standard reasoning under the same GRPO setup: 63.4 vs 60.8 BIRD dev greedy EX, and it reduces syntax errors from 4.5% to 1.9% [P4 §4.3]. The headline 64.9 BIRD EX uses 16-candidate tree decoding, not one call [P4 Table 6]. The setting is single-turn; “interactions” are internal SQL probes [P4 §3.2]. No artifacts are linked.

**P5 GBV-SQL.** A four-agent, training-free pipeline: Planner prunes the schema and decomposes the question; SQLGenerator writes sub-SQL and merges; SQL2TextValidator back-translates SQL and checks intent; SQLChecker repairs execution/format issues [P5 §3.1–3.5]. On BIRD dev it reports 63.23 EX/69.87 VES with DeepSeek-v3, a 5.8-point improvement over MAC-SQL+DeepSeek-v3 [P5 §4.2, Table 1]. The benchmark-quality analysis is separately important: 183 gold errors were found among failed Spider dev items and 62 among passed items; after manual correction only 37 were judged genuine model failures, yielding 96.5/97.6 on the cleaned subset [P5 §4.3]. That cleaning is a sensitivity analysis, not the official score. The paper provides no code link.

## 5. Cross-cutting implications for the project

1. **Execution feedback is the strongest repeated signal, but it is not free.** P2, P3, and P4 all report gains from interleaving execution, and P5’s SQLChecker ablation is the largest component drop on BIRD (63.23→59.65) [P4 §4.3; P2 Table 2; P3 Table 3; P5 §4.4]. But all require database access and extra calls/turns at inference; P1 avoids that by using execution only during training [P1 §3.3]. Test-time access is a separate experimental factor, not a free add-on.
2. **Schema information is consistently useful, but rarely isolated.** P5’s Planner removal costs 1.10 BIRD points [P5 §4.4]; P4’s entity-match reward removal costs 3.1 points from its ablation base [P4 §4.4]; P2’s schema reward removal lowers BIRD majority EX from 64.2 to 62.6 [P2 App. A.8]. These are bundled with other changes. None of the five isolates a reusable, DB-level human schema note, which is the gap the proposed first experiment targets.
3. **Self-reflection without an external anchor is weak evidence.** P1 found a simple CoT prompt did not improve accuracy [P1 §4.2]. Removing P5’s SQL2Text validator costs 1.43 BIRD points (63.23→61.80), but it is coupled to execution checking and a selector [P5 §4.4]. P3’s memory-verification removal costs 2.1 CoSQL points, again in a system with execution feedback [P3 Table 3]. “Ask the model to critique itself” is not supported as a standalone intervention by these papers.
4. **Benchmark quality can dominate error analysis.** P5’s gold-error audit is a warning against treating every execution mismatch as a model failure [P5 §4.3]. Any new BIRD Mini-Dev experiment should retain the official metric but separately audit a sample of discordant failures for ambiguous questions or gold errors, without editing the gold data.
5. **There is no published Mini-Dev 2026 or DeepSeek-API baseline in these papers.** P5 uses DeepSeek-v3, but on BIRD dev with a four-agent pipeline and API calls [P5 §4.1]; that is not a Mini-Dev baseline. The project must measure its own baseline under the same prompt, model snapshot, sample IDs, and execution budget as its variants.
